# 背景

当前项目 `src/` 下存在部分中文被转义为 `\\uXXXX` 的情况，影响可读性。
同时方法缺少清晰的中文注释，降低维护效率。

# 目标

- 修复 `src/` 下中文转义乱码，恢复为可读中文。
- 为 `src/` 下所有方法补充中文注释（方法头 Javadoc + 复杂逻辑行内注释）。

# 范围

- 覆盖 `src/` 下所有方法。
- 排除：构造函数、getter、setter。

# 非目标

- 不修改业务逻辑与功能行为。
- 不进行架构调整或重构。

# 约束

- 全部注释与文档使用中文。
- 保持代码语义一致，注释与实现不冲突。
- 单元测试若执行，单次不超过 60s。

# 方案选择

采用 **方案 A：完全人工逐类阅读 + 手工注释**。

原因：
- 质量优先，避免自动生成“空话注释”。
- 逐段理解逻辑，确保注释准确。

# 执行策略

1. 使用 `rg` 扫描 `src/` 下 `\\u[0-9a-fA-F]{4}` 转义。
2. 逐文件阅读，人工将转义替换为正确中文。
3. 为每个方法补充 Javadoc 注释。
4. 在复杂逻辑处添加行内中文注释，强调“为什么这样做”。
5. 自检注释与代码一致性。

# 注释规范

方法头 Javadoc 至少包含：

- 方法用途（做什么）
- 关键参数含义（对复杂参数重点说明）
- 返回值语义（非空/异常条件说明）
- 异常行为（若存在）

行内注释原则：

- 聚焦关键判断、特殊分支、算法意图
- 解释“为什么”，避免重复代码表面含义

# 乱码修复规范

- 仅替换 `\\uXXXX` 形式的转义中文，不引入语义改动。
- 保持文件为 UTF-8 编码，避免重复转义。

# 质量与验证

- 不引入 TODO/占位注释。
- 重点检查：注释是否准确、是否与代码逻辑一致。

# 风险与回滚

- 风险：人工替换转义时可能误改语义。
- 应对：逐处比对上下文语义，必要时回看 API 文档。
- 回滚：保留改动前版本（若用户要求，可额外备份）。

# 里程碑

- 执行前批量修改确认

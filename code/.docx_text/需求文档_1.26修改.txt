1. 引言
1.1 编写目的
本文档是关于“基于 IGinX 的智能数据和模型关联管理系统”的完整功能与技术规格说明。编写本文档的主要目的如下：
明确功能需求：详尽描述系统在异构数据接入、模型管理以及两者关联机制方面的各项功能要求，确保项目研发目标的一致性。
指导研发流程：作为后续系统架构设计、数据库建模、核心代码编写及模块开发的直接技术依据，避免研发过程中的逻辑偏差。
提供验收准则：本文档定义的各项需求指标将作为系统功能测试、压力测试以及毕业设计最终验收的重要判别标准，对系统的设计、开发与测试具有约束作用，相关参与人员应严格依据本文档开展相应工作。
促进团队沟通：本文档旨在为导师（审核技术方案）、开发人员（理解业务逻辑）以及测试人员（编写测试用例）提供统一的参考基准。
1.2 项目背景
1.2.1 宏观背景与趋势
随着工业互联网与数字化转型进程的加速，现代工业仿真与科学计算领域正经历着从“单一物理场模拟”向“复杂系统数字孪生”的跨越。在这一过程中，系统产生的资产呈现出爆炸式增长与高度多样化的特征：
海量数据：涵盖了高频采样的传感器时序数据、复杂的结果文件、以及关系型的设备配置参数等。
多语言异构模型： 针对不同的计算场景，算法工程师使用了多种技术栈，包括 Python 脚本（用于数据分析）、MATLAB/Simulink（用于控制算法）、C/C++ DLL（用于高性能计算）以及 AMESim（用于物理建模）等。
虽然 IGinX 等新型异构数据管理中间件已经初步解决了底层数据的统一接入与透明访问问题，但数据与算法模型之间依然存在明显的“断层”。
1.2.2 现状与技术痛点
尽管数据与模型是科研与生产的核心资产，但当前的主流方案往往将“数据管理”与“模型管理”割裂对待。数据存储于各类数据库中，而模型文件散落在本地磁盘或版本控制系统中。这种“存储分离、管理脱节”的现状带来了严峻的技术挑战：
异构数据与模型集成困难（数据孤岛效应）：
表现： 不同的模型依赖不同的运行环境与数据接口标准。例如，MATLAB 模型需要特定的 .mat 格式输入，而 Python 脚本可能读取 CSV 或数据库流。
后果： 缺乏统一的接入标准，导致每次调用模型都需要开发专门的数据转换与适配代码，系统集成成本高昂，难以实现跨语言、跨平台的模型协同调用。
数据-模型关联缺失（溯源与复现难题）：
表现： 在实际科研与工程迭代中，模型版本与数据版本处于动态变化中。往往依靠人工记录来标记，如：“模型V1.0使用了数据集A进行训练，使用了数据集B进行验证”。
后果： 这种松散的弱关联极易出错。一旦时间推移或人员变动，常常无法确切得知某个模型输出是由哪个版本的输入数据产生的，导致实验结果不可复现，严重影响科研严谨性与工程安全性。
缺乏元数据标准，模型复用率低（黑盒化问题）：
表现： 大量优质的算法模型以“裸文件”（如 .dll 或 .py）形式存储，缺乏对输入输出接口、物理含义、适用范围等关键信息的标准化描述（元数据）。
后果： 对于非原始开发者而言，模型如同“黑盒”。使用者难以快速检索所需模型，也无法得知如何正确调用该模型，导致重复造轮子现象严重，知识资产沉淀困难。
数据与模型管理割裂：目前数据存储在数据库中，而算法模型通常独立存在于文件系统或镜像库中，缺乏一种直观的映射机制来描述“哪段数据应该由哪个模型处理”。
异构适配难度大：算法模型在调用不同来源的数据时，往往需要编写复杂的适配代码来处理不同数据库的方言和协议，导致模型复用性差。
1.2.3 项目建设目标
针对上述痛点，本项目拟构建一套“基于 IGinX 的数据与模型智能关联管理系统”。 利用IGinX强大的异构数据统一接入能力与文件系统存储特性，打破数据与模型的存储壁垒。通过定义标准化的元模型档案，建立模型与数据的强关联映射，实现从数据导入、模型存储、智能关联配置到自动化调用的全流程闭环管理，从而提升科研与工程效率，实现知识资产的高效复用与可视化管理。
1.3 项目范围
本系统旨在构建一个轻量级、高扩展性的数据与模型关联管理平台。系统边界界定如下：
1.3.1 系统包含的功能
本系统将覆盖以下核心业务流程与功能模块：
数据管理：
支持通过 IGinX 接入并管理数据，提供对底层异构数据库（如 InfluxDB、IoTDB、PostgreSQL 等）的统一连接配置、元数据同步与数据查询服务，重点支持时序数据和结构化数据。
提供数据的批量导入、元数据查看、以及基础的可视化展示（趋势图、数据表格）。
模型管理：
基于 IGinX 的文件系统模式，实现对 Python、C/C++(DLL)、MATLAB、AMESim 等异构模型文件的持久化存储。
提供元模型档案功能，支持对模型的功能、输入输出接口、开发者信息、运行环境依赖等进行标准化定义与编辑。
关联管理：
支持用户自定义创建“数据-模型”关联任务（例如：指定某数据集作为某模型的输入）。
构建多语言适配的执行引擎，能够解析元模型档案，自动加载运行环境并执行模型计算。
可视化服务与接口：
提供基于 Web 的可视化操作控制台。
对外暴露标准的 RESTful API 及 SDK（Python/Java），支持第三方系统集成调用本平台的存储与计算能力。
1.3.2 系统不包含的功能 
为了确保项目的聚焦与可行性，以下功能不在本次系统开发的范围内：
模型内部算法开发：本系统仅负责模型的“管理”与“调用”，不负责具体算法模型（如神经网络结构、物理仿真公式）的编写与优化。
在线代码IDE：系统不支持在 Web 端直接编写或调试 C++/Python 代码，仅支持已调试完成的模型文件上传。
IGinX 内核开发：本系统基于IGinX 提供的现有接口进行上层应用开发，不涉及 IGinX 数据库内核源码的修改。
物理设备驱动开发：系统假设数据已由网关或采集器写入底层数据库，不涉及工业现场物理设备的通信协议（如 Modbus, OPC-UA）解析与驱动开发。
在线模型训练平台：本系统侧重于“模型推理”与“应用管理”，不提供在线的大规模模型训练、标注或超参数调优功能（假设模型已在外部训练完成）。

2. 总体描述
2.1 产品目标
2.1.1 核心目标 
本系统致力于打造一个面向工业物联网场景的算法模型关联与管理中间件平台。 系统的核心目标是打破底层异构数据存储与上层业务算法之间的技术壁垒，依托 IGinX 中间件提供的统一抽象接口，实现对底层异构数据源（时序数据库、关系数据库、文件系统）的透明访问。系统旨在让用户无需关注底层物理设备的差异，即可通过低代码的方式管理算法模型，并实现数据模型的智能关联。
2.1.2 系统架构视角 
为了支撑上述目标，本系统采用经典的 B/S 分层架构设计。系统不直接操作底层物理存储设备，而是作为 IGinX 的上层应用管理系统存在。
系统的逻辑架构具体分为以下四层：
表现层 ：基于 Web 浏览器的前端交互界面。负责数据可视化渲染、表单输入及交互控制，为用户提供可视化的数据、模型管理与规则配置入口。
业务逻辑层 ：系统的核心服务层，包含模型管理、元模型档案解析、关联管理及 API 网关。该层负责解析用户请求，通过本地进程接口动态调度计算资源。
数据接入层 ：由 IGinX 中间件核心构成。本系统通过 IGinX 的 JDBC/Session 接口及文件系统接口，实现对结构化数据和非结构化算法模型文件的统一读写。
基础设施层 ：包含底层物理存储引擎（如 InfluxDB, MySQL, Local FileSystem），提供系统运行所需的算力与存储支撑。


2.2 产品功能摘要
本系统主要提供以下四大核心功能模块，各模块通过元数据驱动实现业务闭环：
数据管理：
支持通过 IGinX 接入多种异构数据库。
提供向导式的数据导入功能，支持时序数据（CSV/Excel）和结构化数据的解析入库。
提供数据的在线预览、检索、导出及基础统计分析功能。
模型管理：
利用 IGinX 的文件系统模式，实现对 Python (.py)、C/C++ (.dll/.cpp)、MATLAB (.m)、AMESim (.ame) 等多格式模型文件的持久化存储。
元模型档案管理：支持对模型的功能、用途、关联数据集、开发者、来源等等信息进行标准化录入与版本管理。
关联管理：
关联配置： 支持用户建立“数据集”与“模型”之间的映射关系（如：训练集映射、验证集映射）。
多语言适配调度： 内置多语言执行适配器，能够解析元模型档案，自动组装输入参数，调用相应的解释器（如 python.exe）或加载器（如 ctypes）执行模型计算。
可视化与开放服务：
多维可视化： 支持数值表格、时序曲线、结果图的渲染展示。
API 集成能力： 对外暴露 RESTful API，并提供 Python/Java SDK，允许第三方服务调用本系统的“存储”与“计算”能力。
2.3 运行环境要求
本系统采用 B/S 架构设计，确保在不同宿主机环境下的兼容性与一致性。
2.3.1 服务器端运行环境 
宿主操作系统：支持 Windows 7 及以上版本、国产操作系统。
核心中间件：IGinX（部署于容器或本地环境中），配置为文件系统 (FS) 存储模式及数据库接入模式。
模型运行时依赖：
针对 Python 模型：需配置 Python 3.x 环境及相关科学计算库（NumPy, Pandas 等）。
针对 MATLAB/AMESim/DLL 模型：需预置相应的运行时库 (Runtime Library) 或兼容层（如 Wine 环境或 Windows Containers），以支持专有格式模型的加载与执行。
2.3.2 客户端运行环境
浏览器：推荐使用 Chrome 80+、Edge (Chromium内核) 或 Firefox 等现代浏览器。
操作系统：Windows 7/10/11,国产操作系统均可访问。
2.3.3 网络与接口环境
网络协议：支持 TCP/IP 协议栈，服务端需开放 HTTP 端口供 Web 访问及 API 调用。
对外接口支持：
RESTful API (HTTP/HTTPS)

2.4 总体用例视图 
本节通过总体用例视图展示系统的核心功能边界及各参与者与系统功能之间的交互关系。
2.4.1 总体用例图 
系统主要包含以下三个核心用例集，各角色与用例的对应关系如下：
参与者：模型工程师
模型托管：上传 Python/C++/DLL/MATLAB/AMESim 等多格式模型文件至 IGinX 文件系统。
元模型档案编辑：创建或更新模型的描述信息（功能、用途、开发者），并声明模型输入所需的初始数据集格式。
元模型档案生成：根据用户声明自动生成标准化的元模型描述文件。
参与者：数据管理员
导入/导出数据：支持时序数据、结构化数据的批量导入与导出。
异构数据源接入与结构管理：配置 IGinX 接入底层的关系型数据库或时序数据库。
数据查询与编辑：允许用户进行差异化的检索与展示。
参与者：算法执行工程师
关联管理：建立“数据集 → 模型”的关联绑定。
关联调用：依据元模型档案定义，触发模型运行。
可视化分析：查看结果，包括数值表格、趋势曲线。
实验报告与资源导出：将计算结果或关联后的模型数据打包导出为指定格式。

2.4.2 核心业务流程 
系统最核心的“模型执行”业务流程如下：
数据准备阶段：数据管理员通过系统导入数据集，系统将其存储于底层数据库并通过 IGinX 建立索引。
模型注册阶段：模型工程师上传“算法模型（如 MATLAB 文件）”，存储至文件系统并生成或编辑元模型档案。
关联编排阶段：算法执行工程师在界面上创建关联规则，将“数据集”与“算法模型”绑定，并指定输出目标为“验证结果”。
执行与展示阶段：系统根据档案描述的顺序调用模型进行计算，将生成的“验证结果”回写至存储层。算法执行工程师随后进行可视化并直观查看效果。

2.5 系统功能结构
2.5.1 功能模块划分 
本系统依据业务逻辑的内聚性，自顶向下划分为五个核心子系统。各子系统及其包含的关键功能模块如下：
1. 数据资源管理子系统
异构数据源接入与结构管理
数据导入与导出
数据查询与编辑
2. 模型资产管理子系统
模型托管 
元模型档案编辑
元模型档案生成
3. 关联管理系统
关联管理
关联调用
4. 可视化分析子系统
数值与曲线分析
实验报告与资源导出
5. 系统基础与集成子系统
开放接口服务 
2.5.2 数据资源管理子系统
该子系统是平台的基础底座，主要负责异构数据的统一接入与治理，确保输入数据的可用性。
异构数据接入与结构管理：利用 IGinX 中间件屏蔽底层差异，支持连接 InfluxDB、IoTDB 等时序数据库，以及 PostgreSQL等关系型数据库，同时支持存储结构的管理。
数据导入与导出：提供可视化的向导界面，支持 CSV、SQL 等格式的数据批量导入，并能将清洗后的数据导出供离线使用。
数据查询与编辑：支持以标准 SQL 或类 SQL 语法对数据进行检索与预览，并提供数据编辑功能。
2.5.3 模型资产管理子系统
该子系统负责管理算法模型及其元数据，是实现“融合”的关键。
模型托管：核心功能之一。支持上传 Python, C/C++, DLL, MATLAB, AMESim 等多语言、多格式模型文件，底层通过 IGinX 文件系统 (FS) 接口实现存储。
元模型档案编辑：引入“元模型档案”概念，支持用户声明模型的功能、用途、开发者信息及关联数据集要求。
元模型档案生成：支持根据用户提供的声明信息或代码注解，自动生成标准化的元模型档案。
2.5.4 关联管理子系统
该子系统是平台的“大脑”，负责处理数据与模型之间的逻辑绑定与任务调度。
关联管理：提供图形化界面，允许算法执行工程师建立数据与算法模型的绑定关系。
关联调用：解析关联规则，相应的计算环境下（如 MATLAB Runtime 或 Python 环境），注入数据并执行任务。
2.5.5 可视化分析子系统
该子系统负责运行结果的多维展示，帮助用户直观理解数据价值。
数值与曲线分析：提供常规的时间序列曲线、散点图及统计表格展示。
资源组合导出：支持将“模型文件 + 关联数据 + 结果报表”打包导出，形成完整的报告。
2.5.6 系统基础与集成子系统
该子系统负责平台的安全管控与对外开放能力。
开放接口服务：提供 RESTful API 及 Java/Python SDK，允许第三方系统通过网络调用本平台的模型计算能力，实现系统集成。

本系统主要面向模型开发者、数据管理员及工程应用人员。根据系统功能模块的划分，核心用户角色定义如下：

4.数据需求
本章详细描述系统涉及的静态数据、动态数据，以及数据库选型、数据字典定义和数据采集方式。
4.1 静态数据
静态数据是指在系统运行过程中相对稳定、不经常改变，主要用于支持系统运行的基础配置和元数据。本系统的静态数据主要包括：
模型元数据
包括模型的唯一标识、名称、版本号、文件类型（如 .py, .dll, .mat）、文件存储路径、接口定义（输入输出参数描述）、上传时间及开发者信息。
关联规则
包括规则 ID、规则名称、关联的模型 ID、映射配置 JSON（定义了 IGinX 时序数据路径与模型输入参数的绑定关系）、结果回写路径配置。
系统基础配置
包括底层 IGinX 中间件的连接信息（IP、端口）、日志保留策略等全局参数。
用户与权限数据
包括用户 ID、用户名、登录密码（加密存储）、所属角色（管理员、算法执行工程师、模型工程师）以及对应的操作权限列表。这是系统安全认证的基础。
4.2 动态数据
动态数据是指在系统运行过程中频繁产生、变化、流转的数据，分为输入数据和输出数据。
4.2.1 输入数据
指进入系统并参与处理的数据流：
时序数据
来源：外部物理设备或网关。
内容：包含时间戳、测点路径和物理数值的连续数据流。
特征：高频写入，数据量大。
用户上传文件
来源：用户通过 Web 前端上传。
内容：包括模型算法文件（.zip,.ame,.py）、历史数据文件（.csv, .xlsx）等。
用户控制指令
来源：用户在界面上的操作。
内容：任务触发指令、任务终止指令、数据查询筛选条件等。
4.2.2 输出数据
指系统处理后产生并提供给用户或外部系统的数据：
结果数据
去向：写入底层数据库存储，并在前端界面以图表形式展示。
内容：经过模型计算后生成的时序结果数据，通常带有任务 ID 标记（如 root.sim_result.job_01.power）。
导出资源包与报告
去向：供用户下载至本地。
内容：PDF 格式的实验分析报告、包含模型文件与数据的 ZIP 压缩包。
系统运行日志
去向：存储于服务器文件系统或数据库。
内容：包括用户操作审计日志、系统异常堆栈信息。
4.3 数据库和管理架构介绍
根据数据的异构特征，本系统采用混合存储架构。
PostgreSQL
类型：开源对象关系型数据库 (ORDBMS)。
用途：存储 4.1 静态数据（如用户信息、规则配置）。
选择理由：具备强大的事务一致性和丰富的数据类型支持（如 JSONB），适合管理复杂的业务逻辑关系。
IGinX
类型：国产开源异构数据管理系统。
用途：统一管理 4.2 动态数据 中的时序数据和非结构化文件。
底层引擎：挂载 InfluxDB 或 IoTDB 存储时序数据，挂载本地文件系统存储模型文件。
选择理由：提供统一的访问接口，屏蔽底层异构数据库的差异，支持高吞吐量的写入。

5. 接口需求
5.1 用户界面
本系统采用 B/S（浏览器/服务器）架构，用户界面通过标准的 Web 浏览器呈现。界面设计遵循简洁、高效、工业化的原则，确保用户能够直观地管理异构数据与任务。

5.1.1 界面标准与规范
前端标准：界面基于 HTML5、CSS3 和 ECMAScript 6+ 标准开发，兼容主流浏览器（Chrome 80+, Edge, Firefox）。
分辨率适配：界面布局以 1920×1080 分辨率为基准进行优化，同时支持响应式布局，能够向下兼容 1366×768 分辨率，确保在不同终端上无内容遮挡或错位。
交互风格：
导航模式：采用左侧垂直导航栏与顶部状态栏相结合的布局。
操作反馈：所有数据提交操作（如保存、删除）必须提供明确的 Toast 消息提示（成功/失败）；高危操作（如删除模型）必须提供模态对话框进行二次确认。
主题风格：默认提供“工业蓝/灰”色调，支持在“明亮模式”与“暗黑模式”之间切换，以适应长时间监控的视觉需求。
5.1.2 主要界面布局逻辑
系统主要包含以下三类核心界面布局：
资源管理类界面（左树右表结构）
适用模块：数据资源管理、模型资产管理。
布局描述：
左侧（20%宽度）：展示资源层级树。支持节点的展开、折叠与右键上下文菜单。
右侧（80%宽度）：展示选中节点的详细信息列表或属性配置表单。支持多列排序、分页查询及工具栏操作（新增、导入、导出）。
可视化分析界面（仪表盘结构）
适用模块：数值与曲线分析、实时监控。
布局描述：
采用 Dashboard 仪表盘布局，核心区域为大尺寸的 ECharts 图表容器。
支持图表区域的缩放、游标测量以及多图表的上下堆叠排列。
顶部或侧边提供时间范围选择器（Time Picker）和图例控制器。
5.2 硬件接口
本系统不直接控制底层的机械部件，而是通过操作系统和驱动程序与服务器硬件及终端设备进行交互。
5.2.1 外部设备连接
传感器与网关：本系统不直接通过串口（RS-232/485）或 GPIO 接口连接物理传感器。所有现场物理设备需先接入工业网关或边缘采集站，由网关通过以太网接口将数据转换为 TCP/IP 数据包后，再发送至本系统。
5.3 软件接口
本系统作为一个基于 Web 的应用平台，依赖于多个外部软件组件来提供数据存储、计算隔离及运行环境支持。
5.3.1 IGinX接口
用途：作为时序数据的统一入口，屏蔽底层 InfluxDB/IoTDB 的差异；同时利用其文件系统功能存储非结构化模型文件。
接口机制：
SDK 调用：后端集成 IGinX 官方提供的 Java/Python Session SDK。
通信协议：基于 Thrift RPC 框架封装的二进制协议。
连接方式：通过 TCP/IP 协议连接 IGinX 服务的 6667 端口。
5.4 API 接口
本节定义系统对外暴露的编程接口，以及系统内部前后端交互的标准接口规范。这些接口允许外部系统（如数据采集网关、第三方调度脚本）与本系统进行数据交换和功能调用。
5.4.1 外部开放接口
为了支持自动化运维和第三方集成，系统提供一套基于 Token 认证的 HTTP 开放接口。
数据写入接口
用途：供边缘网关或脚本向 IGinX 写入时序数据，绕过前端页面上传。
接口地址：POST /api/open/v1/write
请求参数：包含设备路径、时间戳数组、数值数组的 JSON 对象。
响应：状态码 200 表示写入成功；4xx/5xx 表示错误原因。
任务执行接口
用途：根据关联规则请求执行相应的任务。
接口地址：POST /api/open/v1/job/trigger
请求参数：关联规则 ID（rule_id）、时间范围（start_time, end_time）。
响应：返回生成的任务 ID（job_id）及任务状态。
5.4.2 内部 Web API 规范
系统前端与后端之间采用 RESTful 风格的 API 进行交互。
接口设计原则
无状态性：服务器不保存客户端的会话状态，每次请求必须携带认证凭证。
资源导向：URL 使用名词复数表示资源（如 /users, /models），使用 HTTP 动词表示操作（GET 查询, POST 新增, PUT 修改, DELETE 删除）。
统一响应格式
所有 API 的返回结果必须遵循统一的 JSON 结构，以便前端进行标准化的错误处理和数据解析：
{
  "code": 200,          // 业务状态码：200=成功, 401=未认证, 500=内部错误
  "message": "success", // 提示信息：用于前端展示
  "data": { ... }       // 业务数据：对象或数组
}
安全认证
API 请求头必须包含 Authorization: Bearer &lt;JWT_TOKEN&gt;。后端过滤器负责校验 Token 的有效性。
5.5 通信接口
本节定义系统各组件之间以及系统与用户终端之间所采用的网络通信协议。
5.5.1 网络传输协议
HTTP/HTTPS 协议
应用场景：用户浏览器的页面加载、前后端 REST API 调用、文件上传下载。
版本要求：支持 HTTP/1.1，生产环境建议开启 HTTP/2 以提升并发加载性能。
WebSocket 协议
应用场景：任务的实时日志推送和状态变更通知。
机制：在 HTTP 握手成功后升级连接。
心跳保活：客户端需每隔 30 秒发送 Ping 帧，服务器回复 Pong 帧，以维持长连接存活，防止中间网络设备因超时切断连接。
5.5.2 组件间通信协议
TCP/IP 协议
应用场景：Web 后端服务连接 PostgreSQL 数据库（默认端口 5432）和 IGinX 中间件（默认端口 6667）。
约束：后端服务与数据库、中间件应部署在同一高速局域网内，确保低延迟通信。

6.2 安全性需求
本系统管理着核心的算法模型资产和实验数据，且允许执行用户上传的代码，因此安全性尤为关键。
1. 身份认证与访问控制
认证机制：强制启用 JWT (JSON Web Token) 认证，无 Token 或 Token 过期的请求直接拒绝（HTTP 401）。
权限控制：实施基于角色的访问控制 (RBAC)。
管理员：拥有所有权限。
模型工程师：仅能管理模型，不可查看系统底层日志。
仿真工程师：仅能使用模型运行任务，不可删除或修改模型代码。
2. 数据安全
传输加密：所有 HTTP/WebSocket 通信必须通过 TLS 1.2+ (HTTPS) 加密，防止局域网嗅探。
敏感存储：数据库连接串等敏感配置项需加密存储于配置文件中。
审计日志：对所有“写操作”（增、删、改）必须记录审计日志，包含操作人 IP、时间及操作内容，日志不可篡改。
6.3 可靠性需求
1. 可用性指标
系统应达到 99.9% 的可用性（即每月计划外停机时间不超过 43 分钟）。
支持 7×24 小时 连续无人值守运行。
2. 容错与恢复
服务熔断：当底层组件（如 IGinX）无响应超过 5 秒时，系统应触发熔断，返回友好的错误提示，而不是让前端页面假死。
自动重启：后端服务应配置守护进程，在进程异常退出后自动尝试重启。
数据一致性：在“模型上传”或“任务创建”等涉及多步骤的操作中，若中途失败，必须自动回滚数据库事务和文件系统操作，防止产生脏数据。
6.4 可维护性需求
1. 系统日志
后端应输出结构化的分级日志（DEBUG, INFO, WARN, ERROR）。
日志文件应按天归档（Log Rotation），并保留最近 30 天的历史记录以便追溯。
2. 部署便捷性
提供标准的包含 Web 后端、前端、PostgreSQL、IGinX 等所有依赖服务的配置，确保在 30 分钟内完成环境搭建。
3. 代码与文档
后端代码应遵循统一的编码规范（如阿里巴巴 Java 开发手册），核心算法逻辑需有注释覆盖率 &gt; 30%。
提供完整的 API 接口文档（如 Swagger/OpenAPI），方便前后端联调及后续维护。

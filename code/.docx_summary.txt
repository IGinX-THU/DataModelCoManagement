1. 引言
1.1 编写目的
本文档是“基于 IGinX 的智能数据模型关联管理系统”的概要设计说明书。作为软件研发生命周期中承上启下的核心技术文档，其编写目的旨在达成以下目标：
建立需求与设计的双向追踪： 将《需求规格说明书》中明确的业务用例转化为具体的软件模块与技术架构。通过建立需求追踪矩阵 (RTM)，确保每一项业务需求在概要设计中都有对应的功能模块和接口定义，实现从需求到设计的全链路可追溯。
提供工程落地的直接依据： 宏观定义系统的技术架构选型、子系统划分、模块职责边界及核心数据结构。本文档将作为后续详细设计、数据库建模、API 接口定义以及核心代码编写的直接指导文件，规范开发团队的工程实践。
明确验收与测试标准：确立系统在架构层面的技术路线与质量指标（如高并发下的时序写入策略、大文件传输方案），为系统集成测试、性能压力测试以及毕业设计的最终技术验收提供架构级的判别依据。
统一技术语言与架构视图： 为项目导师、架构师、开发人员及测试人员提供统一的系统视图，消除对异构数据处理与模型调度逻辑的理解偏差，确保团队协作的一致性。
预期读者对象：
项目导师：用于审核系统技术方案的合理性与工作量。
系统架构师/核心开发者：用于指导模块划分、接口设计与核心难点攻关。
测试工程师：用于理解系统模块交互逻辑，编写测试用例。

1.2 项目背景与范围
1.2.1 项目背景
随着工业互联网与数字化转型的深入，工业仿真与科学计算领域积累了海量的异构资产：一方面是传感器产生的高频时序数据，另一方面是用于处理这些数据的多语言算法模型（如 Python, MATLAB, C++ DLL 等）。
尽管新型异构数据管理中间件 IGinX 已初步解决了底层异构数据源（如 InfluxDB, IoTDB, PostgreSQL）的统一接入问题，但在实际应用中，“数据”与“模型”依然处于割裂状态：
存储分离：数据存储于数据库，而模型散落在文件系统，缺乏统一管理。
关联缺失：难以追溯某个计算结果是由哪份数据、哪个版本的模型计算得出的，导致实验难以复现。
异构壁垒：不同语言的模型（如 .py 与 .dll）对数据输入的格式要求各异，导致集成调用困难。
本项目旨在构建“基于 IGinX 的智能数据模型关联管理系统”，利用 IGinX 的异构融合能力，打破数据与模型的存储壁垒，实现从数据接入、模型托管、智能关联管理到自动化任务调度的全流程闭环管理。
1.2.2 项目范围
本系统的设计与实现聚焦于“关联管理”与“调度执行”，具体的系统边界定义如下：
包含的功能：
数据资源管理：基于 IGinX 实现对底层时序数据库（InfluxDB, IoTDB）和关系型数据库（PostgreSQL）的统一接入、结构管理与数据导入导出。
模型资产全生命周期管理：利用 IGinX 文件系统特性，实现多语言模型文件（Python, MATLAB, DLL ,AME等）的分布式存储、版本控制及元数据解析。
关联管理：提供可视化界面建立“时序数据-模型参数”的映射规则，并内置多语言执行引擎调度计算任务。
可视化分析：提供计算结果的时序曲线对比分析及实验报告导出功能。
不包含的功能：
模型内部算法开发：系统仅负责模型的“管理”与“调用”，不提供在线编写、调试或优化算法模型内部逻辑（如神经网络结构设计）的功能。
IGinX 内核开发：系统基于 IGinX 提供的现有 SDK 进行上层应用开发，不涉及 IGinX 数据库内核源码的修改。
物理设备驱动：系统假设数据已由网关写入底层数据库，不直接涉及工业现场物理设备（如 PLC, 传感器）的通信协议驱动开发。

1.4 设计方法论与追踪策略
为了确保系统设计能够完整覆盖《需求规格说明书》中的业务目标，并为后续的代码开发提供精确指导，本文档在编制过程中严格遵循以下设计方法论与追踪策略：
基于 RTM 的双向追踪机制： 本文档在第 3 章各子系统的设计中，引入了 需求追踪矩阵。
正向追踪：每一个核心设计模块（Module/Service）都必须显式声明其服务的需求用例编号（如 DATA-ACCESS-001），确保所有需求都有对应的代码实现载体。
反向追踪：每一个核心接口（API）与数据库实体（Entity）的设计，都必须能够回溯到具体的需求来源，避免出现无用的“镀金”设计。
“契约优先”的接口设计原则： 在详细编码之前，本文档第 4 章先行定义了模块间的接口契约。这包括输入/输出参数的定义、异常处理规范以及数据传输对象（DTO）的结构。这种设计确保了前后端开发可以并行进行，并降低了模块间的耦合度。
工程化落地导向： 本文档超越了传统的“纯文本描述”，设计内容不只停留在概念层，而是直接映射为开发工具中的工程骨架，使其具备极强的可执行性。
结构化与标准化：本文档采用了高度结构化的描述方式（如使用表格定义接口、使用 Mermaid 语法绘制流程图、使用 JSON Schema 定义数据结构），以提高设计文档被用户阅读和理解的准确性。
2. 总体架构设计
2.1 系统逻辑架构
本系统基于 分层解耦 设计思想，自上而下将系统划分为表现层、业务逻辑层、数据接入层与数据存储层。各层之间通过定义良好的接口协议进行交互，上层只依赖下层的抽象，严禁跨层调用，以保障系统的可维护性与底层异构中间件的可替换性。
1. 表现层 (Presentation Layer)
职责： 作为系统的用户交互界面，采用 Vue 3 + Element Plus 构建单页应用。本层通过 7 大核心业务页面 实现对 WBS 中所有业务功能的完整覆盖，辅以底层的 UI 逻辑组件与通信适配层，实现交互与数据的分离。
1.1 核心业务页面 (Core Business Views) 
(1) 主页
用户功能：
关键指标概览：查看模型资产总数、任务调度成功率、系统健康状态等 KPI 指标。
调度趋势分析：通过图表查看近期任务调度的负载量与时间分布。
最新动态：查看系统最新的任务执行记录摘要。
(2) 关联规则编排页
用户功能：
创建关联规则：通过向导建立数据源与模型参数的绑定关系。
编辑关联规则：修改已有的参数映射逻辑或触发条件。
查询关联规则：支持按规则名称、关联模型进行检索。
规则拓扑展示：可视化展示“输入数据流 -> 算法模型 -> 输出数据流”的逻辑结构。
执行算法任务：手动触发选定的关联规则，提交计算任务。
(3) 数据资源管理页
用户功能：
异构源接入：注册 InfluxDB/IoTDB/PostgreSQL 数据源，并执行连接状态测试。
数据源维护：查看数据源配置详情，或卸载不再使用的数据源。
存储结构预览：预览数据源内部的测点目录树或表结构拓扑。
数据查询与编辑：对时序数据或结构化数据进行分页查询与在线修正。
离线数据流转：支持时序/结构化数据文件的离线导入，或将在线数据导出为文件。
(4) 模型资产管理页
用户功能：
模型文件托管：上传 .py/.dll/.ame 等多格式算法模型文件，支持下载与移除操作。
接口自动解析：自动解析代码文件，提取输入/输出参数定义。
元模型档案管理：查看及人工编辑元模型的功能描述与接口定义 (Schema)。
版本管理：查看模型版本列表，执行不同版本间的元数据差异对比。
(5) 任务监控页 (TaskMonitorView)
用户功能：
任务状态监控：实时查看后台计算任务的运行状态（排队/运行/成功/失败）。
任务终止：对运行异常或超时的任务执行强制终止操作。
日志审计：查询与筛选任务的详细运行日志与异常堆栈信息。
(6) 可视化结果分析页 (AnalysisView)
用户功能：
结果可视化：渲染单次任务计算结果的时序曲线图。
多任务对比：选择多个任务进行结果叠加对比，支持时间轴自动对齐。
实验报告生成：生成包含统计指标与图表的 PDF 实验报告。
资源包导出：打包下载包含模型源码、输入数据及结果数据的完整资源包。
(7) 系统设置页 (SettingsView)
用户功能：
用户权限管理：配置用户角色及其对应的功能访问权限。
系统日志审计：查询系统级的关键操作审计日志。
开放接口服务：查看 RESTful API 文档，管理 SDK 接入鉴权凭证。
1.2 UI 逻辑组件 (UI Logic Components) 本层提取各页面通用的交互逻辑，支撑页面运行。
可视化引擎 (Viz Engine)：封装 ECharts，负责关联拓扑图交互与百万级时序数据降采样。
状态存储 (Pinia Store)：管理 User Session、当前选中的关联上下文及资源缓存。
1.3 通信适配 (Communication Adapter) 本层负责与后端 API 进行标准化通信。
API 网关适配器 (Gateway SDK)：基于 Axios 封装，负责请求标准化与响应解包。
安全适配器 (Security Adapter)：负责 JWT 令牌自动注入与 HTTP 异常熔断。
2.业务逻辑层 (Business Layer)
职责： 系统的“大脑”，基于 Spring Boot 框架构建。该层承载了核心业务规则与流程编排，通过模块化设计将五大子系统解耦，每个子系统内部进一步划分为若干细粒度服务 (Services)，以实现单一职责与高内聚。
2.1 数据资源模块：
异构数据源服务: 处理多类型数据库的注册、连接保活 (Keep-alive) 及安全卸载。
数据资源服务: 提供数据的分页查询、编辑能力，并集成策略模式实现多格式离线数据的导入导出。
2.2 模型资产模块：
模型文件服务: 基于 IGinX 文件系统实现算法文件的分布式存储与物理删除。
元模型档案服务: 提供代码自动解析引擎（提取 Input/Output Schema）及版本差异比对 (Diff) 能力。
2.3 关联管理模块：
关联规则服务: 管理绑定关系的 CRUD，执行严格的数据类型兼容性校验。
算法任务服务: 维护计算任务的全生命周期（提交/排队/执行/终止），管理任务状态机流转。
2.4 可视化分析模块：
可视化分析服务: 提供时序数据降采样算法及多任务结果对齐逻辑。
资源导出服务: 集成 PDF 报表生成引擎与 ZIP 打包引擎。
2.5 系统基础模块：
权限与日志服务: 基于 RBAC 实现接口访问控制，并采集关键操作审计日志。
3.数据接入层 (Adapter Layer)
职责：作为系统的统一防腐层。本层通过 IGinX 提供的标准接口实现全类型数据的统读统写，屏蔽底层的物理连接细节与异构差异。
核心组件：
IGinX Unified Adapter (统一适配器)：
系统的唯一数据出口。封装了 IGinX Session SDK，负责建立与 IGinX Server 的通信会话。
它接收上层的业务请求，将其路由分发为对应的 IGinX 操作指令（如 SQL 查询元数据、insertRecords 写入时序数据、uploadFile 上传模型）。
Metadata SQL Builder (元数据构造器)：
负责将对系统核心实体（如用户、档案、规则）的 CRUD 操作组装为标准 SQL 字符串。
该组件构建的 SQL 语句经由 Unified Adapter 透传给 IGinX 执行，实现对 PostgreSQL 中元数据的间接访问。
4.数据存储层 (Infrastructure Layer)
职责：提供系统运行所需的计算与存储资源。IGinX Server 在此层作为核心异构数据内核，通过多协议适配器向下管理物理资源。
1.核心组件：
IGinX Server (异构数据内核)：
关系型引擎 (Relational Engine)：通过 JDBC 驱动连接 PostgreSQL，执行元数据的存储与查询，利用 PostgreSQL 处理复杂的关联关系与 JSONB 数据。
时序引擎 (Time-Series Engine)：集成 Native SDK (如 IoTDB Session / InfluxDB HTTP Client)，实现对时序数据的高吞吐写入与降采样查询。
文件引擎 (File System Engine)：通过 本地 File I/O 或 Thrift RPC 协议，管理分布式的非结构化模型文件（.py/.dll），提供统一的文件流读写服务。
2.物理存储节点：
PostgreSQL: 物理存储业务元数据。
InfluxDB / IoTDB: 物理存储海量时序数据。
Local Disk / HDFS: 物理存储模型资产文件。

工程开发约束：
依赖方向原则：
modules 层依赖 framework 层与 common 层。
framework 层依赖 common 层。
严禁反向依赖（如 common 层不能引用 modules 中的类），防止循环依赖。
IGinX 隔离原则：
业务层 (modules) 的 Service 代码中，禁止直接 import IGinX 原生 SDK 的类（如 cn.edu.tsinghua.iginx.session.Session）。
所有对 IGinX 的操作必须通过 framework.iginx 包下的 IginxStorageWrapper 进行调用。这确保了当 IGinX SDK 升级或 API 变更时，只需修改适配层代码，无需侵入业务逻辑。
对象模型分层原则：
DTO (Data Transfer Object)：仅用于 Controller 层的入参接收，必须包含 JSR-303 校验注解。
VO (View Object)：仅用于 Controller 层的出参响应，屏蔽敏感字段。
Entity：仅用于 Service 层与数据库交互，禁止直接暴露给前端。

2.5.2 详细流程交互说明
1. 数据导入与索引建立阶段
参与角色：数据管理员 
业务目标：将离线数据集（时序数据/结构化数据）接入系统并建立索引。
交互流程：
表现层 (Presentation)：
管理员在 DataEditorView 中唤起导入向导，上传 CSV/Excel 文件。
前端组件解析文件头，生成列映射配置，向后端提交 ImportDataDTO。
业务逻辑层 (Business Logic)：
DataSourceController 接收请求。
DataService 根据数据类型（时序/关系型）选择对应的解析策略。
基础设施层 (System/IGinX)：
存储数据：IginxStorageWrapper 将解析后的数据通过 insertRecords（时序）或 SQL（关系）写入底层数据库。
建立索引：IGinX 自动为新写入的测点路径（Path）建立索引，使其可被检索。
2. 模型资产注册与档案管理阶段
参与角色：模型工程师 
业务目标：实现算法文件的物理存储与元数据档案的标准化定义。
交互流程 A：上传算法模型文件
表现层：工程师在 ModelAssetsView 上传 .py/.dll/.ame 文件。
业务逻辑层：ModelAssetService 接收文件流，进行MD5校验。
基础设施层：调用 IginxStorageWrapper.uploadFile()，将物理文件写入 IGinX 的文件系统，并返回唯一文件 URI。
交互流程 B：创建/编辑“元模型档案”
表现层：工程师在界面上定义模型的输入/输出参数（Schema）、适用场景等信息。
业务逻辑层：MetaProfileService 接收 JSON 数据。
基础设施层：将元模型档案信息（Meta-Profile）通过 SQL 写入系统的关系型元数据表中（通过 IGinX 或 直接连接 PG）。
3. 关联规则编排阶段
参与角色：算法执行工程师 
业务目标：建立数据与模型的逻辑绑定，并确保类型安全。
交互流程：
表现层：
工程师在 AssociationView 中选择“数据源测点”与“模型输入参数”，创建映射关系。
业务逻辑层：
AssociationService 接收规则配置。
校验有效性：系统自动比对数据源的数据类型（如 String）与模型要求的输入类型（如 Float）是否兼容。若不兼容，直接拦截并报错。
基础设施层：
校验通过后，TaskDao 将关联规则对象序列化，通过 IGinX 接口（或 JDBC）将规则配置持久化至关联关系库。
4. 仿真任务触发与执行阶段
参与角色：算法执行工程师 
业务目标：调度计算资源，执行模型逻辑，并回写结果。
交互流程：
表现层：工程师点击“触发仿真任务”，指定时间窗口。
业务逻辑层 (核心调度)：
解析档案：ExecutionEngine 读取元模型档案，确定输入输出格式。
注入数据：通过 IginxStorageWrapper 从底层拉取指定时间段的原始数据，生成输入文件。
执行计算：启动本地进程（Python/Matlab Runtime）加载模型文件进行计算。
基础设施层：
回写结果：计算完成后，系统捕获输出结果，将其写入 IGinX 的结果存储区（Result Storage）。
5. 可视化分析阶段
参与角色：算法执行工程师 
业务目标：验证计算结果，对比不同任务的性能指标。
交互流程：
表现层：工程师在 AnalysisView 选择任务。
业务逻辑层：AnalysisService 从 IGinX 读取“原始输入”与“计算结果”。
表现层：前端 VizChart 组件渲染数值指标与时序对比曲线，完成业务闭环。

3.1.2 核心类与接口设计
本子系统设计了五类核心服务组件，分别负责数据源的生命周期管理、结构定义、数据流转、查询检索及维护操作，以支撑异构数据的全链路管理。
1. 数据源生命周期管理组件 (DataSourceService)
对应需求：DATA-ACCESS-001 (注册异构数据源), DATA-ACCESS-002 (移除异构数据源)
设计职责：
连接管理：负责处理用户提交的数据源配置信息（如 IP、端口、鉴权信息），并负责对密码字段进行加密处理。
连通性探测：在注册前调用底层网络库测试与目标数据库（InfluxDB/IoTDB/PostgreSQL）的物理连通性。
挂载与卸载：调用 IGinX 接口完成存储引擎的挂载；在移除数据源时，负责执行“引用完整性检查”，查询系统元数据，确保该数据源未被任何关联规则引用，防止误删导致业务中断。
2. 存储结构管理组件 (StructureService)
对应需求：DATA-ACCESS-003 (管理存储结构)
设计职责：
异构适配：根据数据源类型（时序型或关系型），屏蔽底层的结构差异。
结构变更：针对时序数据库，负责创建或删除存储组（Storage Group）及测点路径；针对关系型数据库，负责执行 DDL 语句以管理表结构。
3. 数据流转服务组件 (DataImportService & DataExportService)
对应需求：DATA-IMPORT-TS-001 (导入时序数据), DATA-IMPORT-STR-001 (导入结构化数据), DATA-EXPORT-001 (导出数据文件)
设计职责：
导入引擎 (DataImportService)：负责解析外部上传的离线数据文件（CSV/Excel）。该组件根据文件扩展名及目标数据源类型，自动选择解析逻辑，将文件流转换为标准的 IGinX 写入指令（如 insertRecords 或 insertRow），并处理批量写入时的缓冲与内存控制。
导出引擎 (DataExportService)：负责数据的提取与格式化。接收用户的导出请求（包含时间范围、测点列表），从底层存储中拉取数据，并将其序列化为符合 RFC 标准的 CSV 文件或 Excel 工作簿文件流，供前端下载。
4. 统一查询服务组件 (DataQueryService)
对应需求：DATA-QUERY-TS-001 (查询时序数据), DATA-QUERY-STR-001 (查询结构化数据)
设计职责：
统一入口：作为上层业务（如可视化子系统）获取数据的唯一通道，屏蔽底层查询语言（SQL vs IQL）的差异。
时序查询优化：针对时序数据查询，负责处理时间范围过滤，并内置数据降采样逻辑（当返回数据点过多时自动聚合），以减轻网络传输压力。
安全查询：针对结构化数据查询，负责构建参数化的查询条件，防止恶意 SQL 注入。
5. 数据编辑服务组件 (DataMaintainService)
对应需求：DATA-MAINT-TS-001 (编辑时序数据), DATA-MAINT-STR-001 (编辑结构化数据)
设计职责：
数据修正：处理对单条或批量数据的修改与删除请求。
操作审计：作为高危操作的执行者，该组件负责在执行物理删除或更新前，触发审计日志记录机制，确保所有数据变更操作可追溯（记录操作人、时间、影响范围）。

对应需求：MODEL-HOST-001 (上传模型文件), MODEL-HOST-002 (下载模型文件), MODEL-HOST-003 (移除模型资产)
设计职责：
物理存储映射：负责与 IGinX 文件系统交互，将用户上传的算法文件（.py, .dll 等）写入分布式文件系统，并生成统一的访问 URI（如 iginx://models/...）。
版本控制：维护模型文件的版本序列。当上传同名模型时，自动计算版本号递增逻辑（v1.0 -> v1.1），并维护 model_asset 表中的版本历史记录。
引用检查：在执行模型删除操作前，检查 association_rule 表，确保该模型未被任何调度任务锁定，保障资产安全。
2. 元模型档案服务组件 (MetaProfileService)
对应需求：MODEL-PROFILE-001 (编辑元模型档案), MODEL-PROFILE-002 (查看元模型详情), MODEL-PROFILE-003 (版本对比), MODEL-GEN-002 (手动调整档案)
设计职责：
元数据管理：负责对模型的描述信息、开发者信息以及最核心的输入/输出接口定义（Schema）进行 CRUD 操作。
Schema 校验：在保存档案时，负责校验 JSON 格式的接口定义是否符合系统规范（如数据类型是否合法、必填项是否完整），防止脏数据入库。
差异比对：负责加载两个不同版本的元模型档案，对比其输入/输出参数的变化（新增、删除、修改），并生成结构化的差异数据供前端展示。
3. 代码解析引擎组件 (CodeParserEngine)
对应需求：MODEL-GEN-001 (自动解析生成)
设计职责：
自动化提取：该组件负责读取源代码文件的内容，根据文件类型（Python 脚本、MATLAB 脚本等）调用相应的解析逻辑。
接口识别：通过词法分析或正则匹配，自动提取代码中的入口函数参数（Inputs）和返回值（Outputs），并尝试推断数据类型，生成初始的 ParsedMetaDTO 对象，辅助用户快速建立模型档案，减少人工录入成本。

3.3.2 核心类与接口设计
本子系统设计了规则编排、任务管理、调度控制与执行引擎四个核心组件，协同完成从“静态配置”到“动态计算”的转化。
1. 关联规则服务组件 (AssociationService)
对应需求：ASSOC-CONFIG-001 (创建关联规则), ASSOC-CONFIG-002 (管理关联规则)
设计职责：
规则维护：负责关联规则的创建、修改、启用与禁用操作。
兼容性校验中心：这是本组件的核心职责。在创建规则时，它负责获取模型的输入定义（Model Requirements）和数据源的测点类型（Data Characteristics），并进行严格的比对（例如：模型要求输入 Float，但数据源是 String 类型，则拒绝创建），确保计算任务在运行时不会因类型错误而崩溃。
2. 任务生命周期管理组件 (TaskService)
对应需求：SIM-EXEC-001 (执行算法任务 - 提交阶段), SIM-EXEC-002 (终止算法任务 - 控制阶段)
设计职责：
任务实例化：接收用户的计算请求，根据关联规则生成唯一的 TaskID，并在任务日志表中创建一条状态为 PENDING 的记录。
状态流转：负责监听和更新任务的运行状态（PENDING -> RUNNING -> SUCCESS/FAILED），并记录任务开始时间与结束时间。
3. 任务调度器组件 (TaskScheduler)
对应需求：SIM-EXEC-001 (执行算法任务 - 调度阶段)
设计职责：
并发控制：维护一个待执行任务队列。该组件负责根据服务器的计算资源（CPU/内存）限制，控制同时运行的任务数量，防止过载。
异步分发：从队列中获取待执行任务，并将其提交给后端执行引擎进行异步处理，确保 Web 服务的响应线程不被阻塞。
4. 多语言执行引擎组件 (ExecutionEngine)
对应需求：SIM-EXEC-001 (执行算法任务 - 运行阶段), SIM-EXEC-002 (终止算法任务 - 进程管理)
设计职责：
环境准备：负责从 IGinX 下载模型文件到本地临时工作目录。
数据注入：根据关联规则，从 IGinX 查询指定时间范围的时序数据，并将其格式化为模型可读取的输入文件（如 input.csv）。
进程托管：负责启动外部计算进程（如 Python 解释器或 MATLAB Runtime），监控进程的标准输出与错误流，并处理进程的超时与强制终止。
结果回写：在计算结束后，解析模型生成的输出文件，将结果数据回写入 IGinX 的指定结果路径。

1.异构数据源的注册与连通性测试。 
特点：展示 module-datasource 如何穿透到 framework 层与外部 Infrastructure 交互。
异构数据源注册与挂载交互时序图
本图展示了 数据资源管理子系统 (Module: Datasource) 如何作为上层业务与底层基础设施之间的桥梁，完成异构数据源的接入。设计重点在于体现“物理连通性探测”与“逻辑挂载”的两阶段处理机制。
交互流程说明：
物理探测 (Physical Probe)：在正式挂载前，DataSourceService 首先尝试与目标数据库（如 InfluxDB, PostgreSQL）建立 TCP 连接。这一步是为了确保网络层面的可达性，防止因网络防火墙或配置错误导致的挂载失败。
逻辑挂载 (Logical Mounting)：确认连通后，通过基础设施适配层 (IginxStorageWrapper) 向 IGinX 中间件发送 ADD STORAGE ENGINE 指令。此时，IGinX 负责接管该数据源的元数据映射，实现对底层异构差异的屏蔽。
安全存储：最后，连接凭证（如密码）经过 AES-256 加密后，由 DataSourceService 持久化存储至系统元数据表中，确保敏感信息不以明文形式暴露。
2.模型文件上传与物理存储。 
特点：展示 module-model 如何利用 IGinX 的文件系统特性进行存储。
模型文件上传与持久化交互时序图
本图展示了 模型资产管理子系统 (Module: Model) 如何利用 IGinX 的文件系统特性（FS Mode）来管理非结构化资产。设计重点在于展示 Web 文件流到 IGinX 分布式块存储的转换过程。
交互流程说明：
流式传输：用户上传的大体积模型文件（如 .dll, .ame）通过 Controller 进入系统。
协议转换：IginxStorageWrapper 充当协议适配器，将标准的 Java InputStream 转换为 IGinX 支持的文件块写入指令 (Write File Block)。这种设计允许系统处理超过内存限制的大文件。
元数据同步：文件写入成功后，IGinX 返回统一资源标识符（URI, 如 iginx://models/...）。ModelAssetService 随即将此 URI 与业务元数据（版本号、描述）绑定存入关系型数据库，保证了“物理文件”与“逻辑资产”的一致性。

特点：这是典型的Module-to-Module交互。展示 Task 模块如何调用 Model 和 Data 模块的接口，而不直接访问对方数据库。
关联规则创建与类型兼容性校验交互图
本图是系统模块间解耦的最佳实践示例。展示了关联与调度子系统 (Module: Task) 在不直接访问其他模块数据库的前提下，如何通过服务接口（Service Interface）获取所需信息来完成业务校验。
交互流程说明：
需求获取：AssociationService 调用 模型子系统 的 MetaProfileService.getInputSchema() 接口，明确当前模型“需要什么样的输入参数”（如：参数 speed 需要 FLOAT 类型）。
供给获取：AssociationService 调用 数据子系统 的 DataQueryService.getDataType() 接口，查询用户选定的测点“实际是什么类型”（如：测点 root.v.s 是 TEXT 类型）。
核心校验：在关联子系统内部执行比对逻辑。若发现“需求”与“供给”类型不匹配，直接抛出业务异常，阻断规则创建。此流程确保了所有持久化的关联规则在运行时都是类型安全的。

特点：展示 Analysis 模块如何聚合 Task 和 Data 模块的信息来组装图表。

交互流程说明：
上下文反查：前端仅提供 TaskID，分析服务首先调用 调度子系统 的 TaskService，反查该任务的执行上下文（Context），从而获知该任务具体使用了哪些“输入测点”和产生了哪些“输出路径”。
数据拉取：获取路径信息后，分析服务调用 数据子系统 的 DataQueryService，批量拉取这一时间段内的原始数据与结果数据。
数据组装：分析服务将分散的数据流合并、对齐时间轴，最终封装为前端图表组件（ECharts）可直接渲染的 VizDataVO 对象返回。这种设计将复杂的数据处理逻辑封装在后端，减轻了前端的计算压力。
4. 接口设计规范
4.1 接口交互标准
为了实现前后端分离开发的解耦，系统所有 HTTP API 必须遵循以下基础交互契约。所有的响应数据（无论是成功还是异常）都必须包裹在统一的 JSON 结构中。
4.1.1 统一响应结构 (Result<T>)
系统在 com.xmu.iginx.assoc.common.api 包中定义了统一泛型封装类 Result<T>。所有 Controller 层的方法必须返回该对象。
类定义 (Java Signature):
public class Result<T> implements Serializable {
    private Integer code;   // 业务状态码
    private String msg;     // 提示信息（面向用户）
    private T data;         // 业务数据负载
    private Long timestamp; // 响应生成时间戳
    // 快捷构造方法
    public static <T> Result<T> success(T data) { ... }
    public static Result<?> error(Integer code, String msg) { ... }
}
JSON 响应示例:
{
  "code": 200,
  "msg": "操作成功",
  "data": {
    "id": 1001,
    "name": "PID模型v1.0"
  },
  "timestamp": 1704067200000
}

5.2.2 存储策略
1. 分库分表策略
管理数据（PostgreSQL）：
系统元数据量级较小（万级以内），采用单库单表模式，暂不涉及分库分表。
时序数据（IGinX）：
利用 IGinX 的分布式特性，底层对接多个 InfluxDB/IoTDB 实例。系统根据数据的时间戳和设备路径自动路由，实现逻辑上的水平分片。
2. 分区策略
针对 task (任务表)：
该表数据随时间线性增长，且历史日志查询频率随时间衰减。
采用 Range Partitioning (按范围分区) 策略，以 start_time 为分区键，按月 自动创建分区表（如 task_202510）。
目的：提升近期任务的查询性能，便于定期归档或清理旧日志。
3. 索引设计
唯一索引：
sys_data_resource(mount_path)：防止挂载路径冲突。
sys_user(username)：确保用户名唯一。
复合索引：
task(rule_id, start_time)：加速“查询某条规则的历史执行记录”的操作。
全文索引：
association_rule(mapping_json)：针对 JSONB 字段建立 GIN 索引，支持对绑定参数的高效检索。
5.2.3 数据完整性设计
1. 约束规则
非空约束 (NOT NULL)：核心业务字段（如文件路径、连接配置、任务状态）强制非空，防止空指针异常。
引用约束：
ON DELETE RESTRICT：当删除一个“模型资产”时，如果该模型已被“关联规则”引用，数据库将拒绝删除操作，强制用户先解除关联，保障业务逻辑闭环。
2. 触发器/存储过程
本系统主要逻辑在应用层（Java）实现，尽量减少对数据库存储过程的依赖，以保持数据库无关性。
例外：在 sys_user 表使用触发器实现 update_time 字段的自动更新。
3. 数据一致性机制
事务管理：涉及多表操作（如：注册数据源 = 写入 PG + 调用 IGinX）使用 Spring @Transactional 管理事务。
最终一致性：对于跨系统操作（如应用层与 IGinX），采用“重试机制 + 补偿日志”策略。若 PG 写入成功但 IGinX 挂载超时，系统记录异常日志，由后台守护线程定期重试挂载，确保状态最终一致。

5.3.2 数据访问接口
为了保证程序内部数据流转的一致性与安全性，系统定义了严格的数据访问接口规范。
1. 数据交换格式
前后端交互：统一采用 JSON格式。
日期时间规范：
数据库存储：TIMESTAMP , BIGINT (IGinX, 毫秒级时间戳)。
接口传输：统一序列化为 ISO-8601 标准字符串（如 2025-10-01 12:00:00），便于前端直接展示和处理。
大数值处理：针对超过 2^53 的 64 位整数（如数据库主键 ID），在序列化为 JSON 时强制转为 String 类型，防止前端 JavaScript 精度丢失。
2. 编码规范
程序内部采用分层对象模型，严禁将数据库实体直接暴露给前端。
DO (Data Object / Entity)：
用途：与数据库表结构一一对应（如 ModelAsset 类）。
范围：仅在 DAO 层（Mapper）与 Service 层之间流转。
DTO (Data Transfer Object)：
用途：前端向后端传输数据的容器（如 ModelUploadDTO）。
规范：仅包含业务需要的字段，且必须包含 JSR-303 校验注解（如 @NotNull）。
VO (View Object)：
用途：后端向前端展示数据的容器（如 TaskResultVO）。
规范：剔除敏感信息（如密码字段、内部版本号），增加计算字段（如将 status=1 转换为 statusDesc="运行中"）。
3. 校验规则
数据存入数据库前，必须经过三层校验“漏斗”：
L1 接口层校验 (Format Validation)：
使用 Hibernate Validator 注解。
例：IP 地址格式是否合法、端口是否在 1-65535 之间、文件后缀是否为 .py。
L2 业务层校验 (Logic Validation)：
在 Service 内部执行。
例：结束时间必须晚于开始时间；关联的模型参数必须与数据测点类型兼容（Float vs Float）。
L3 数据库层校验 (Constraint Validation)：
依赖数据库约束。
例：mount_path 唯一性约束、外键引用完整性约束。

6. 安全架构设计
本章定义系统的多纵深防御体系。系统基于 Spring Security 与 AOP 切面技术，在接入层、业务层和数据层构建三道防线，确保工业数据资产与算法模型的机密性、完整性与可用性。
6.1 身份认证架构
对应场景：用户登录与 API 调用鉴权。 
责任模块：framework.security (安全框架组件)
6.1.1 无状态认证机制
系统采用 JWT (JSON Web Token) 标准实现前后端分离架构下的无状态认证。
令牌颁发：
用户通过 /api/v1/auth/login 提交凭证。
后端验证通过后，生成包含 User ID、Role 及 Exp (过期时间) 的 JWT，并使用服务器私钥进行 HMAC-SHA256 签名。
请求拦截：
部署 JwtAuthTokenFilter (继承自 OncePerRequestFilter)。
拦截所有受保护接口，解析 HTTP Header 中的 Authorization: Bearer <Token>。
架构约束：过滤器必须在 Spring Security 过滤器链的 UsernamePasswordAuthenticationFilter 之前执行。
6.1.2 会话生命周期管理
有效期策略：Token 有效期设定为 2 小时，兼顾安全性与工业现场操作的连续性。
主动失效机制 (黑名单)：
鉴于 JWT 的无状态特性，后端维护一份 Redis 黑名单 (Key: auth:blacklist:{token}, TTL: 剩余有效期)。
当用户执行“注销”或“修改密码”操作时，系统将当前 Token 写入 Redis。过滤器在校验签名通过后，需额外检查 Redis 黑名单，若存在则抛出 401 Unauthorized。

7. 性能架构设计
本章定义系统在特定负载下的响应能力与处理效率。鉴于系统“低频高计算”与“海量时序吞吐”的业务特性，性能设计聚焦于 计算资源的隔离保护 与 大数据流的内存防爆。
7.1 并发处理架构
系统采用 IO 密集型与 CPU 密集型分离 的双层并发架构，防止重计算任务阻塞 Web 服务线程。
7.1.1 Web 层并发
对应指标：支持 50 人 同时在线操作。
责任组件：framework.web (内嵌 Tomcat 容器)
设计策略：
利用 Spring Boot 默认的 Servlet 线程模型处理 HTTP 请求。
配置约束：设置 server.tomcat.threads.max=200，connection-timeout=20000ms。
适用场景：元数据查询、页面跳转、简单的 CRUD 操作。此类请求响应快，占用线程时间短。
7.1.2 计算层并发
对应指标：支持 5-10 个 并行算法任务。
责任组件：module-task.TaskScheduler (任务调度器)
设计策略：舱壁模式 (Bulkhead Pattern) 隔离。
独立线程池：计算任务不复用 Web 容器线程，而是提交至独立的 ThreadPoolTaskExecutor。
池化配置：
Core Pool Size: N - 1 (N为 CPU 核数，预留 1 核给 OS 和 DB)。
Queue Capacity: 100 (有界队列，防止 OOM)。
拒绝策略：当队列满时，直接抛出 SystemBusyException (HTTP 503)，触发前端熔断提示，保护服务器不被压垮。
7.2 响应延迟处理
7.2.1 异步任务提交机制
针对耗时较长（分钟级）的算法任务，系统采用 “异步提交 + 状态轮询” 模式，确保 API 接口响应时间 < 200ms。
交互时序设计：
7.2.2 读写分离与缓存
元数据缓存：针对 DeviceType、MetaProfile 等低频变动的配置数据，使用 Spring Cache (@Cacheable) 缓存至 JVM 堆内存 (ConcurrentHashMap)，减少 PG 数据库查询压力。
大跨度查询限制：在 DataQueryService 中强制校验 TimeRange，限制单次查询最大跨度为 30 天。若用户需要查看全年数据，前端需通过分段请求实现，防止单次 SQL 查询超时阻塞。
7.3 高吞吐量数据流转 
7.3.1 离线导入内存防爆
对应指标：支持 50MB+ CSV/Excel 文件导入，防止 OOM。 
责任模块：module-datasource
传统误区：一次性将 Excel 读取到 List<Object> 再写入，极易导致堆内存溢出。
本系统设计：SAX 事件驱动模式。
集成 EasyExcel 组件，注册 AnalysisEventListener。
分批写入策略：
监听器按行读取文件流。
在内存中累积至 BATCH_SIZE (如 1000 条)。
触发 IginxClient.insertRecords() 批量写入 IGinX。
立即 clear() 内存列表，GC 可回收。
7.3.2 报表导出流式输出
对应指标：支持导出 万级 数据报表。 
责任模块：module-datasource.DataExportService
设计策略：分页游标 + 流式写入。
严禁全量查询 (SELECT *)。
后端通过 LIMIT 2000 OFFSET N 循环从 IGinX 拉取数据。
每拉取一页，立即写入 HttpServletResponse.getOutputStream()。
客户端浏览器会看到下载进度条持续增长，而服务器内存占用始终维持在单页数据的大小 (KB 级)。
7.4 瓶颈分析与自适应降级
7.4.1 可视化渲染降级 
风险点：工业模型输出可能包含 10万+ 数据点，前端 ECharts 渲染会导致浏览器卡顿甚至崩溃。 
优化策略：LTTB 自适应降采样。
位置：module-analysis.AnalysisService。
逻辑：
检测查询结果集大小 N。
若 N > Threshold (如 2000 像素宽)：
启用 LTTB (Largest-Triangle-Three-Buckets) 算法，将 N 个点压缩为 2000 个特征点。
返回压缩后的数据集，既保留了波峰波谷特征，又保护了前端性能。
7.4.2 进程启动优化
风险点：Python 解释器冷启动耗时 (1-2s)。 
优化策略：按需启动。
考虑到本系统为离线分析系统，用户对“10秒还是11秒”不敏感，但对“系统稳定性”极度敏感。
决策：不维护复杂的 Python 常驻进程池（避免僵尸进程和内存泄漏风险），而是采用 ProcessBuilder 按需启动。虽然牺牲了 1 秒启动时间，但换来了极高的系统稳定性与开发简单度。

8. 可靠性与容错架构设计
本章定义系统的健壮性保障机制。鉴于系统需运行在 Windows/单机服务器环境，且强依赖外部异构组件（IGinX, PostgreSQL, Python Runtime），设计重点在于“连接保活”、“过载保护”与“无状态恢复”。
8.1 运行稳定性架构 
系统采用 “无状态服务 + 自动重连代理” 的架构模式，确保在底层组件波动或服务重启时，业务不中断或能快速自愈。
8.1.1 中间件断连自动恢复
故障场景：IGinX 服务因升级或崩溃重启，或 PostgreSQL 数据库网络短暂不可达。 
责任模块：framework.iginx (IGinX适配层), framework.datasource (连接池)
数据库层 (PostgreSQL)：
策略：利用 HikariCP 连接池的健康检查机制。
配置：
connection-timeout: 30000ms (容忍短暂网络抖动)。
max-lifetime: 1800s (强制定期重连，防止防火墙切断长连接)。
validation-query: SELECT 1。
时序数据层 (IGinX)：
策略：在 IginxClientAdapter 中实现 应用级重试机制。
状态机逻辑：
探测：在执行读写操作捕获到 SessionException 或 TException 时，标记连接失效。
挂起：暂停当前线程 1秒 (Exponential Backoff 指数退避)。
重连：尝试重新执行 session.open()。
失败判定：若连续重试 3次 仍失败，向上抛出 IginxServiceUnavailableException，由全局异常处理器接管。
IGinX 重连状态机
8.1.2 无状态服务恢复
故障场景：Java 后端服务因更新发布或 Bug 崩溃后重启。 
责任模块：framework.security
设计：后端完全摒弃 HttpSession，采用 JWT 令牌认证。
效果：
用户侧：服务重启期间，用户浏览器持有的 Token 依然有效。服务恢复后，用户点击下一个按钮时即可无缝继续操作，无需重新登录。
任务侧：正在执行的计算任务若被中断，状态会停留在 RUNNING。系统重启后，通过 StartupRunner 扫描并重置僵尸任务状态为 FAILED，提示用户重新提交，保证数据一致性。

8.3 业务降级与熔断
故障场景：突发的大量计算请求或海量数据查询导致内存/CPU 资源耗尽。 
责任模块：module-task, module-analysis
8.3.1 计算拥塞熔断
机制：有界队列拒绝策略。
逻辑：
TaskScheduler 维护一个容量为 100 的阻塞队列。
当队列满时，新的提交请求直接触发 熔断。
反馈：抛出 SystemBusyException，API 返回 HTTP 503 Service Unavailable，并在前端提示“系统繁忙，当前排队任务过多，请稍后重试”。
8.3.2 可视化渲染降级
机制：LTTB 自适应降采样。
逻辑：
前端请求查询结果时，后端 AnalysisService 检查数据点数 N。
若 N > 100,000 (前端渲染崩溃阈值)，系统自动降级处理模式。
执行降采样算法，仅返回 2000 个特征点，确保图表能正常展示趋势，牺牲局部精度换取系统可用性。
8.4 异常处理与反馈体系
系统构建三级异常防御网，防止底层技术错误直接暴露给最终用户。
8.4.1 全局异常屏蔽
责任模块：common.exception
组件：GlobalExceptionHandler (@RestControllerAdvice)。
策略：
已知业务异常 (如 RuleNotFoundException)：返回 code: 400, msg: "规则不存在"。
未知系统异常 (如 NullPointerException, SQLException)：捕获堆栈，打印 ERROR 日志（含 TraceID），向前端返回统一的模糊提示 code: 500, msg: "系统内部错误，请联系管理员 (Ref: {TraceID})"。
8.4.2 前端防御性交互
责任模块：presentation.web
策略：
网络错误：Axios 拦截器捕获 timeout/network error，显示全局 Toast “网络连接失败，请检查网络设置”。
资源缺失：当图表加载数据失败时，ECharts 容器显示“暂无数据或加载失败”占位图，禁止白屏。
